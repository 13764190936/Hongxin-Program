# 开发日志 DEVLOG

> **这份文件是干什么的**：让下一个人（或另一个 AI）不用问，就能知道这个项目被改过什么、为什么改、验证到什么程度、还剩什么没定。
>
> **规则**
> 1. **只追加，不修改历史条目**。写错了就新开一条纠正。
> 2. 每条一个编号，日期 + 主题 + 对应提交 hash。
> 3. 固定用下面 6 个三级标题，方便机器解析：`做了什么` / `为什么` / `文件变更` / `验证` / **`未验证`** / `待决` / `下一步`。
> 4. **`未验证` 必须诚实写**。没测过的说没测过，不要用"应该没问题"含混过去。这一节比 `做了什么` 更重要。
> 5. 不写"完成了 XX 系统"这种话。只写"做了什么文件、跑了什么检查、结果是什么"。

---

## 给接手的 AI：你需要先知道的 6 件事

1. **项目**：微信小程序「鸿心徒步」从零重建。徒步步数 + 队伍竞争 + 排行榜激励，外加在线课堂、共读打卡、两类笔记、动态、个人中心。
2. **当前阶段**：只有文档和一个静态 HTML 原型。**没有一行业务代码、没有后端、没有数据库、没有小程序 AppID。** 不要把原型当成已实现的系统。
3. **最大的坑**：文档里 12 个排行榜（B01–B10，B08 拆三格）**必须各自独立**。已确认 B08c 与 B01 的数值和顺序不同，绝不能共用一个统计函数。普通笔记（N 系列）与学习笔记（C 系列）也**不可合并列表**。
4. **规则来源**：`docs/PRD.md` 与 `docs/FEATURE_INVENTORY.md`。里面严格区分【已观察】【入口已见】【重建建议】【待确认】。**不要把"重建建议"当成旧系统事实，也不要把"待确认"补成合理设计。**
5. **12 个待决问题**在 `docs/DECISIONS.md`，每条都给了建议默认值，但**都还没被负责人确认**。未确认前不要写死业务规则。
6. **约定**：虚构测试数据；不连旧生产系统；不提交凭据/真实手机号/私钥；未经授权不注册账号、不买资源、不部署。
