# 鸿心课程行动平台需求记录

- 记录日期：2026-11-04
- 文档状态：已确认需求记录，未代表实现。
- 文档边界：需求、业务决策、验收与开发进度归 GitHub 项目文档；教学概念、练习与掌握程度归 `LEARNING.md`。
- 实现边界：本文记录的是需求，不是已实现功能清单；不据此宣称功能已经开发、测试、上线或验证有效。

## 1. 客户、课程与目标

- 客户是企业培训机构。
- 课程内容是员工动力与综合素养培训，不是业务技能培训。
- 平台用于支持课后习惯持续实践，帮助学员持续行动、维持动力。
- 主要学员类似中国保险从业人员。
- 打卡记录不等于对真实行为的证明；不得宣称平台已经证明真实行为，也不得宣称产品效果已经得到验证。

## 2. 已确认的行动与激励场景

- 5:31 早起打开平台打卡。
- 跑步打卡。
- 阅读学习打卡。
- 客户拜访打卡。
- 队伍与排名是重要激励机制，排名比较已是目标群体现有体系的重要部分。
- 5:31 早起判定沿用仓库既有的 `[05:31:00, 05:32:00)` 半开区间，本轮未变更；待讨论的是容差等默认值，旧窗口已确认，不得倒退。
- 晨跑采用运动软件截图作为凭证的方向已确认；其他行动的凭证要求、晨跑截图具体规则、队伍组织方式及榜单具体规则仍待确认，不能由上述场景描述自行推定。

### 晨跑截图凭证（2026-11-04 本轮确认）

- 运动软件截图是晨跑完成的必需凭证，不采用仅手填里程作为完成依据。
- 截图须经系统识别和校验后，才能判断当天是否完成；上传成功不等于完成。
- 系统需要识别同一截图重复上传，以及截图数字异常或疑似伪造。
- 具体数值阈值以后讨论，本轮不预设。
- 以下规则均待确认，不预设已选择：识别日期与当日的关联方式；支持的运动软件与截图格式；重复检测范围（本人跨日、跨人）；数字异常规则；识别失败与异常的后续处理。
- 防重与异常检测仅用于降低风险，不能保证截图真实，也不能证明本人实际跑步。

### 微信步数累计排行（2026-11-04新增需求）

- 用户明确新增步数排行榜：步数按累计口径统计，并希望优先从微信步数读取数据，加入用户称为“总排行榜”的展示。
- 本轮仅确认“步数累计排行”和“优先使用微信步数作为数据来源”的意向。微信步数接入可行性、用户授权、读取与同步规则均未验证；不得声称已经接入微信步数，也不得预设能够自动后台读取。
- “总排行榜”的具体含义、排名对象（个人或队伍）、累计周期（课程期或长期等）、展示与统计范围均待讨论；同步去重、补传和缺失数据处理规则也待讨论。
- “总排行榜”不得据此解释为跨企业或全国排行，也不得解释为早起、跑步、阅读等行动的混合综合分。DEC-13 与 DEC-15 继续保留；如需变更，须由用户另行明确确认。
- 既有晨跑截图凭证规则全部保留。微信步数是否影响晨跑完成判定尚未确认，不能代替或取消运动软件截图及其识别校验要求。
- 旧 DEC-04 中人工补录、上限、步长等内容仅为建议，不属于本轮确认事项；本轮不据此确定任何具体规则。

## 3. 角色与协作需求

### 学员

- 参与课后习惯实践并完成相应打卡。
- 打卡是核心使用场景。

### 保险公司主管

- 主管是产品用户。
- 主管需要通过可视化 UI 收到未完成打卡的提醒，并看到谁没有完成打卡。
- 主管与助教共同跟进学员。

### 培训机构助教

- 助教与保险公司主管共同跟进学员。
- 助教与主管的具体职责分工尚未确认。

### 培训机构

- 培训机构只需要数据，不建设培训机构专用管理 UI。
- “不需要培训机构专用管理 UI”不等于“主管也不需要 UI”，两类角色的需求不得混同。
- 数据以接口、导出或其他方式交付，以及数据格式、频率和范围，均待确认。

## 4. 未完成打卡识别与提醒需求

- 系统需要自动识别并统计未完成打卡。
- 主管需要以可视化 UI 接收提醒，并查看未完成打卡的人员。
- 提醒时间、提醒渠道、提醒入口和可见范围尚未确认。
- 截止前提醒、截止后统计或其他时点的选择，不在本稿中预设答案。
- 本条是待实现与待验收的需求，不表示现有系统已具备自动识别、统计或提醒能力。
