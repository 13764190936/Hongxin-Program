## 1. 四个行动项

| 项目 | 单位 | 有效条件 | 单日上限 | 重复提交 | 异常处理 | 进榜 |
|---|---|---|---|---|---|---|
| **早起** | 次 | 客户端时刻落在北京时间 `[05:31:00.000, 05:32:00.000)` | 1 次 | 幂等键去重 | 窗口外 → **422 拒收，不落库**；时刻与服务端偏差 >180s → `pending_review` | 是（次数） |
| **晨跑** | 公里 | 距离 >0、时长 ≥1 分钟、步数为正整数、必须有图片引用 | 未定（暂不限制） | 幂等键去重 | 缺图/负数/非整数 → 422；OCR 为模拟 → `pending_review` | 是（里程） |
| **阅读** | 分钟 | 计时 ≥60 秒 | 未定（暂不限制） | 幂等键去重 | <60 秒 → 422；未勾选"完成任务" → 记 `valid` 但 `metrics.completed=false` | 是（时长） |
| **拜访** | 次 | 员工自主申报，无凭证 | **1 次** | 同一天第二次 → 409 | 不校验真实到访 | **否** |

**关于早起的 59 秒窗口（重要）**

- 窗口是半开区间，`05:31:59.999` 算，`05:32:00.000` 不算。
- 判定用**客户端点击时刻**（Q3）。代价是客户端改时间就能作弊。
- 因此加了一条审计兜底：客户端时刻与服务端接收时刻相差超过 180 秒，记录仍保存，但状态转 `pending_review`，原因写 `client_clock_behind` / `client_clock_ahead`。这样既按你的决策判定，又不会让改时间的记录混进榜单。
- **不改容差、不加宽限**。要放宽必须你明说，我不会偷偷加。

**关于阅读（诚实说）**

时长来自客户端计时，改个变量就能刷。当前只用于"记录"，用于排行时请当作参考值。要防刷需要服务端心跳，那是另一件事。

**关于拜访**

不验证真实到访，所以不进榜。如果以后要进榜，我建议单独成榜，不要混进其他三项。

## 2. 状态机

```
提交 ──► valid           计入排行
      ├─► pending_review 待人工核（不计入排行）
      └─► 422 拒收       不落库（窗口外、参数非法）
```

| 状态 | 含义 | 计入排行 | 谁能改 |
|---|---|---|---|
| `valid` | 通过全部校验 | ✅ | 运营可改（需留痕，未实现） |
| `pending_review` | 有异常标记，等人工看 | ❌ | 运营可批准/驳回（接口未做） |
| 422 拒收 | 不满足硬条件 | — | 不能改，需重新提交 |

`rejected` 已预留但当前没有路径写入——被拒的不落库。留它是为了以后"先落库后审核"改法时不用改表。

## 3. 排行口径

| 项 | 定义 |
|---|---|
| 对象 | `team` = 队内成员；`enterprise` = 企业内各团队 |
| 指标 | 只支持 `early_count`（次）、`run_km`（公里，2 位小数）、`read_minutes`（分钟，整数） |
| 周期 | `day` = 当天；`week` = 周一起 7 天 |
| 业务日 | 一律 `Asia/Shanghai`，由服务端计算，不信客户端 |
| 只统计 | `status = 'valid'` |
| 排序 | 值降序 |
| 并列 | 同值同名次，下一名跳号（1、1、3） |
| 资格 | 未入队 → 空榜 + 说明文字，不报错 |
| 团队归属 | 按**提交时**的团队记录（转队不追溯历史） |
| 综合分 | **不存在**。请求 `metric=composite` 直接 422 |
| 跨企业 | **不存在**。`scope=national` 直接 422 |

**未定的**：单日上限、并列是否真的同名次（业务上可能要按提交时间破平）、周榜是否跨月累计、团队榜要不要改成人均。

## 4. 幂等与并发

- 每次提交必须带 `idempotencyKey`。
- 唯一索引 `(user_id, idempotency_key)`：同一用户同一键重复提交，返回**第一次的记录**，HTTP 200 + `idempotent: true`，不会产生第二条。
- 并发加入团队：`team_members` 主键 `(team_id, user_id)`，重复插入不会重复计数。

## 5. 权限边界（服务端强制）

| 操作 | 员工 | 管理员 | 实现位置 |
|---|---|---|---|
| 看自己的记录 | ✅ | ✅ | `repo.listMyRecords` 按 `user_id` |
| 看全企业记录 | ❌ 403 | ✅ 仅本企业 | `repo.listEnterpriseRecords` 强制 `enterprise_id` |
| 导出 CSV | ❌ 403 | ✅ 且写 `export_logs` | `repo.exportCsv` |
| 加入其他企业团队 | ❌ 403 | ❌ 403 | `repo.joinTeam` 校验 `enterprise_id` |

**当前鉴权是测试适配层**：请求头 `X-Test-User` 直接传用户 id。这不是正式鉴权，接微信登录后必须换成服务端签发的会话。但即使在测试层，所有查询也都带 `enterprise_id`，跨企业读写在数据访问层就被挡住。
