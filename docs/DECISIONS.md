## 2. 逐条问题与建议默认值

说明：每条给一个**具体问题**和一个**建议默认值**。你可以直接回「按建议」，或只改其中几条。建议默认值的立场是"能上线、能验收、不虚构旧规则"；不代表现有系统就是这样。

### DEC-01 品牌与主体

**问**：这个小程序服务的是**一家企业内部的员工**，还是**对外开放给任何徒步爱好者**？

- 若是内部：需要组织身份校验（白名单或邀请码），榜单只在本组织内可比。
- 若对外开放：所有榜单是平台级的，需要处理"陌生人能不能看到我的昵称/步数"。

**建议默认值**：先按**单一组织内部**做，不实现多企业隔离，但数据模型保留 `org_id` 字段（留空），将来要隔离时不用改表。

**依据**：文档提到"宏丰企业学习平台""上海鸿风教育"，但名称与现名「鸿心徒步」的关系未确认（PRD §2.3）。

**首版做**：首页（含三个队伍榜）、徒步活动、队伍创建/加入/详情（含两个队内榜）、在线课堂、共读（含单书榜）、动态、两类笔记、个人中心（含三个排行页签、资料、留言板）。

### DEC-03 排行榜口径（最重要的一条）

**问**：12 个榜里，哪些是"当天"、哪些是"活动期间累计"、哪些是"历史累计"？

**建议默认值**（可逐行改）：

| 榜 | 建议周期 | 备注 |
|---|---|---|
| B01/B02/B03/B04/B05 | 本次徒步活动期间累计 | 首页三榜与活动页共用同一活动范围；B03 分母用队伍全部成员 |
| B06 队内总步数 | 活动期间累计 | 与 B01 同周期，便于对照 |
| B07 队内今日 | 当天（Asia/Shanghai 自然日） | 零步成员**显示**并排末位 |
| B08a 今日排行 | 当天，对象=个人 | 取"今日步数>0 的用户" |
| B08b 个人排行 | 活动期间累计 | 固定显示"我的名次"条 |
| B08c 队伍排行 | 待你指认 | 文档只记录"数值与顺序不同于 B01"，**不能据此推断是按人均还是另一时间范围**。我上一版写成"按人均"是过度推断，已撤回。此条必须先定 |
| B09 共读首页打卡排行 | 跨书目的用户总打卡天数 | 最可能的解释，但**需你确认** |
| B10 单书打卡排行 | 该活动周期内的累计打卡天数 | 同分并列占同一名次，下一名跳号 |

**通用约定建议**：业务日统一 `Asia/Shanghai`；榜单每日 00:05 生成快照，页面显示"数据截止 11-03 00:05"；不分页，首屏 50 名 + 我的名次。

**为什么 B08c 要特别标出来**：文档明确写了它和 B01「数值与顺序明显不同」。如果两个榜其实是同一个东西，那是现有版本的 bug；如果不是，就一定有别的口径。我不能替你选。

### DEC-04 步数来源

**问**：步数到底从哪来？

| 选项 | 说明 | 代价 |
|---|---|---|
| A. 微信运动（`wx.getWeRunData`） | 需用户授权，只能拿到近 30 天 | 稳定，但要用户每天授权一次，容易断签 |
| B. 手动上传 | 用户自己填/点"点我上传步数" | 简单，但可作弊，排行榜意义下降 |
| C. 旧系统自有数据源 | 需旧系统还活着并开放接口 | 与"不连旧生产系统"冲突 |
| D. 第三方硬件/手环 | 需 SDK | 成本高 |

**建议默认值**：**A 为主 + B 兜底**。用户授权微信运动 → 每天首次进入小程序自动拉取 → 允许当天手动补录一次（覆盖而非累加）。里程按 `步数 × 0.6m` 估算，配置化。

**依据**：M12 页面叫"微信运动授权"但面板里没有微信运动项，说明现有实现**可能**没接；所以这条必须你确认，我不猜。

**必须同时定的 4 个细节**（建议值）：

1. 同一天多次同步 → **以最后一次为准，不累加**
2. 跨天补传 → **只接受当天，历史日期不可补**（否则榜单可被刷）
3. 单日有效步数上限 → **50000 步，超出按上限计并标记**
4. 公里换算 → **0.6 米/步**，集中配置

### DEC-06 课程与共读的关系

**问**：「在线课堂」和「共读」是两个独立内容体系，还是共读也算一种课程？

**建议默认值**：**两套独立**。

- 「我的学习」（M06）= 在线课堂
- 「我报名的共读」（R13）= 共读
- 两者不合并列表，只在个人中心并列展示

**理由**：两者公开目标不同（学习广场 vs 打卡排行），指标不同（已听人数 vs 打卡天数），合并会让"我学了什么"变成一锅粥。

---

### DEC-07 共读结束后的行为与打卡计数（最容易出错的一条）

**问 1**：《中庸》2026-06-13 已结束（今天 2026-11-03）。结束后还能读、能报名、能打卡、能上榜吗？

**建议默认值**：结束后 —— **可阅读、可看榜、不可报名、不可打卡**。榜单冻结在结束日的快照。

**问 2**：规则写"不限打卡次数"，但排行统计的是"天"。同一天打 3 次卡算几天？

**建议默认值**：**次数按行数、天数按 `biz_date` 去重**。同一天多次打卡 → 次数 3、天数 1。排行用天数，个人页可显示次数。

**理由**：如果不分开，"不限次数"会让榜单被一个人刷满，失去意义。

### DEC-09 留言板

**问**：它是公开留言墙，还是私密意见反馈？

**建议默认值**：改成**私密反馈**。用户只看到自己的留言与官方回复，看不到别人的。运营角色可回复、可标记已处理。

**理由**：现在"任何用户都能看到别人的留言，且每条都显示删除按钮"，在实名组织内是隐私风险（AT06/AT10 都过不了）。

**如果你要保留公开**：至少做到 —— 只能删自己的、回复仅运营可见、不显示真实姓名。

### DEC-11 / DEC-12 迁移与接续

**问**：旧系统的用户、步数、打卡、笔记，要不要搬过来？

**建议默认值**：**首版不迁移**。旧用户用微信登录后是全新账号，看不到历史数据。

**理由**：

1. 文档没写旧系统的数据能否合法导出（DEC-11 本身就是待确认）。
2. 迁移没做核对脚本前，风险高于收益。
3. 新系统先跑通，再谈"补历史"——历史数据补进来会让榜单口径更复杂。

**如果你要迁移**：请先确认旧系统是否还在运行、是否有导出权限、能否拿到 `openid` 与手机号的对应关系。这三样缺一样，迁移都做不了。
