## 2. 我对项目功能结构的理解

### 2.1 一句话

一个**以徒步步数为核心激励、以队伍为单位竞争、以课程和共读为内容供给**的企业/组织内部小程序。排行榜是产品的激励中枢，不是附属页面。

### 2.2 五入口结构（G01–G05，已观察）

```
首页  ├ 身份摘要 + 今日/累计步数 + 上传步数（H01–H04）
      ├ 今日参与人数 / 今日里程（H07–H08）
      ├ 三个队伍榜：总步数 / 总人数 / 平均步数（B01/B02/B03）← 三个独立口径
      └ 课程栏目 ×3：业绩突破 / 阳明心学 / 父母和孩子教育（H12–H17）
共读  ├ 宣传位 + 热门书目（R01/R02）
      ├ 打卡排行（B09 未核实）+ 最新打卡（R04）
      ├ 书目详情：介绍 / 单书榜（B10）/ 最新打卡（R10）/ 规则（R11）
      └ 我报名的共读 → 开始学习（R13–R15）
动态  └ 活动参与记录流（D01–D05），字段=头像/昵称/时间/活动名/步数
笔记  ├ 笔记广场（N02）+ 我的笔记（N03）
      └ 发布：正文 + ≤3 图 + 仅自己可见（N10–N14）
我的  ├ 摘要（M01/M02）→ 我的徒步 / 我的队伍（M03/M04）
      ├ 我的排行：今日 / 个人 / 队伍（B08a/B08b/B08c）← 三个独立页签
      ├ 我的学习（M06）、我的资料（M07–M11）
      └ 微信运动授权（M12）、留言板（M13–M16）
```

### 2.3 二级结构（不进底栏）

- **徒步活动**（W01–W07）：届次主题、活动累计步数/公里、里程类比、参与总人次、热门队伍（B04）、更多队伍（B05）。
- **队伍详情**（W18–W28）：封面/口号/名次摘要/发起人/邀请/分享/加入/捐步/队内榜（B06+B07）/证书（W28）。
- **在线课堂**（C01–C15）：课堂封面、成员区、学习广场、我的笔记、发布学习笔记。

### 2.4 三条必须守住的关系

1. **排行榜不可合并**：B01/B02/B03 是首页三个页签；B08b/B08c 是"我的排行"里另外两个页签，其中 **B08c 与 B01 数值和顺序明显不同**——文档已明确记录这一点。B04/B05 是同一批队伍在活动页的另两种呈现。B06/B07 是队内成员榜。B09 未知。B10 是单书榜。**共 10 个（B08 拆三格，实际 12 个视图）**，全部独立定义口径。
2. **两类笔记不可合并**：普通笔记公开到**笔记广场**，学习笔记公开到**学习广场**且必须带课堂关联。可共用编辑组件，不可共用列表与业务归属。
3. **记录流 ≠ 排行榜**：最新打卡（R04/R10）和动态（D01）是时间流，不是成绩榜；证书（W28）是独立功能。

### 2.5 我判断优先级最高的一件事

**步数从哪来、怎么去重**（DEC-04）决定了一半模块的可行性。文档里"M12 微信运动授权"打开的面板中**没有微信运动项**，只有位置和相册权限。这意味着现有版本可能根本不是走微信运动接口。如果这一点不定，排行榜、动态、队伍贡献全部没有数据源。这是第一个必须解决的问题。

## 5. 技术方案

### 5.1 推荐方案（首版）

**原生微信小程序（TypeScript）+ 微信云开发（云函数 / 云数据库 / 云存储）**

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | 原生小程序 + TypeScript + Less | 第一版只有小程序一端，跨端框架（Taro/uni-app）带来的构建复杂度换不到收益；原生组件性能与调试体验最好，踩坑资料最多 |
| 状态/请求 | 轻量自封装（`request` 封装 + 页面级 store），不引 Redux/MobX | 页面数量约 20 个，状态简单，引入状态库是负担 |
| 服务端 | 云函数（Node.js 18） | **不买服务器、不备案域名、不配 HTTPS**，符合"不购买资源"的约束；`wx.cloud` 自带 `OPENID`，不用自建登录态 |
| 数据库 | 云数据库（文档型） | 榜单是读多写少，用"原始记录 + 定时物化快照"两段式即可；不必上 MySQL |
| 存储 | 云存储 | 笔记图片、头像、队伍封面 |
| 定时任务 | 云函数定时触发器（每日 00:05 Asia/Shanghai） | 生成当日/周期榜快照 |
| 后台管理（后续） | 云函数 HTTP 触发器 + 一个纯静态网页 | 不引入新服务器；先不做 |

**为什么不做自建 Node + MySQL**：需要买服务器、买域名、做 ICP 备案、配 HTTPS、自己维护进程和备份。你现在不需要碰命令行，但所有线上故障最后都要落到"有人去修"。云开发把这层拿掉了。等真的需要 Web 运营后台、或要接企业微信/钉钉时，再迁不迟——数据模型设计时已经和存储解耦。

**成本**（下表为量级判断，**未核实具体报价，正式投入前需在腾讯云控制台确认**）：

| 项 | 量级 |
|---|---|
| 小程序注册（个人/企业主体） | 0 元；企业主体需认证费 |
| 云开发基础版 | 有免费额度，小规模使用大概率 0 元/月；超量按量计费 |
| 域名/服务器/备案 | **不需要**（云开发不吃自有域名） |

> 我在方案里不放具体价格数字：价格会变，而且我不想给你一个会被当成承诺的数。真要买，我先去查当时的实际报价再报给你。

**风险与代价（诚实说）**：

1. 绑定微信生态。将来若要做 App/H5，云开发的部分能力要重写。
2. 云数据库查询能力弱于 SQL，"平均步数"这类聚合要在云函数里算，或预计算快照。
3. 云开发冷启动有延迟，首屏可能需要骨架屏撑住（原型已体现加载态）。
4. 一旦用户量上来，云开发单价高于自建服务器。

## 7. 本轮原型的说明（重要）

**它是什么**：一个单文件 HTML，用虚构数据把 20 个页面画出来，用来评审信息结构和交互位置。左右两侧可切换页面与状态。

**它不是什么**：不是小程序代码，不能编译、不能提交表单、没有数据库、没有网络请求、没有任何真实用户数据。**所有按钮的提交行为都只是弹出一个说明框。**

**覆盖情况**：

| 项 | 覆盖 |
|---|---|
| 页面 | 20 个（5 个底栏 + 15 个二级页） |
| 排行榜 | B01–B10 全部，B08 拆 a/b/c 三个页签，**每个榜独立口径卡**，B09 只画空位不填数 |
| 两类笔记 | 笔记广场（N02）与课堂学习广场（C03）分开，"我的笔记"两套分开 |
| 状态 | 加载中 / 空列表 / 加载失败 / 无权限 / 活动已结束（《中庸》按文档日期为已结束） |
| 待确认标注 | 虚线标签，鼠标悬停看具体缺什么 |

**刻意的取舍**（你可能想知道为什么）：

- **B09 不填数字**。填了就会被当成规则。宁可空着。
- **B08c 用了一套和 B01 完全不同的数据**。为了让"这不是同一个榜"这件事看得见。
- **《中庸》显示"已结束"**。文档写它 2026-06-13 结束，今天是 2026-11-03。按规则它就是结束了，而"结束后能不能打卡/上榜"是 DEC-07，所以我禁用按钮并标注，不替你决定。
- **B07 的零步成员保留了**。文档说现有页面零步数会出现，我先按现状画，是不是该过滤等你定。
- **没有画队长视角、后台、注册登录**。这些文档里完全没有证据，画出来就是编。
