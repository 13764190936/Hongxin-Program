- 立场：以下区分【事实核查】【可行性判断】【我的意见】。意见部分不等于结论，最终由负责人定。

## 0. 一句话结论

方向本身成立，且比"复刻旧版徒步小程序"更值得做——**旧版是在猜一个已存在的产品，新版是在定义一个自己的产品**。
但当前这版把最难的三件事（综合分口径、跨企业排行、早起 59 秒窗口）都留在了"未定"，而它们恰好是产品成立与否的关键。**技术不难，规则难。**

## 1. 主要变化（事实核查）

| 维度 | 旧（v0.1/v0.2 原型） | 新（action-preview） | 性质 |
|---|---|---|---|
| 产品主线 | 徒步步数 + 队伍竞争 + 排行榜 | **课程关联的每日行动打卡**（早起/晨跑/阅读/拜访） | 换赛道 |
| 用户 | 单一组织内部 | **其他企业员工，预留多企业** | 换商业模式（B2B） |
| 核心闭环 | 上传步数 → 队伍榜 | 看到任务 → 行动 → 上传/记录 → 后台统计 → 表格与排行 | 加了一个"后台"角色 |
| 导航 | 首页/共读/动态/笔记/我的（5 tab） | **今天/课程/排行/团队/我的**（5 tab） | 内容模块被砍掉 |
| 形态 | 375px 手机竖屏框 | **1120px 响应式，桌面侧栏 + 窄屏底栏** | 桌面优先的 Web |
| 交付物性质 | 功能复刻原型 | 新形态设计提案 + 后端接手说明 | 从"还原"转"定义" |

**被砍掉的**：共读打卡、两类笔记、动态、留言板、徒步证书、课程播放。
**被保留的**：队伍/团队（升级为课程团队）、排行榜（升级为多范围）、个人中心。

> 这是我这轮最想确认的一件事：**共读和笔记是真的不做，还是先放第二版？** 文档没有明确说"砍掉"，只是新前端里没有。如果是延期，TASKS 里那 18 条（T-216…T-218、T-345/T-346）要标"延期"而不是"阻塞"；如果是不做，要标"不做"。现在它们悬着。

## 2. 做得好的地方（具体，不是客套）

1. **早起窗口用半开区间 `[05:31:00, 05:32:00)` 表达**，并明确"涵盖最后一秒的小数部分"。这是对的，比写 `<=05:31:59` 严谨——`05:31:59.5` 不会被漏掉。
2. **明确写了"不能暗改成宽限时间"**。这条很关键：59 秒窗口一定会有边界争议，最容易被开发偷偷加 30 秒宽限，然后产品逻辑就烂了。文档提前把这条路堵住。
3. **前端把"模拟"标到了牙齿**：`previewbar` 常驻、OCR 写"固定示例值，并非从图片中提取"、上传写"仅本机预览"、排行写"布局示意/示例值"。这比 v0.2 在默认视图里藏掉全部标注要诚实得多。
4. **阅读把"时长"和"任务完成"拆成两个独立记录**，并写"不会用达到某个分钟数自动判断完成"。这个拆分是对的，否则"挂机刷时长"就等于完成。
5. **工程性比上一版好**：状态集中在一个 `state` 对象、`esc()` 统一转义、`aria-live` 播报、`focus-visible` 焦点环、`prefers-reduced-motion`、禁用态用 `disabled` 而不是只改样式、`dialog` 用原生元素。

## 3. 可行性判断

| 层 | 判断 | 依据 / 条件 |
|---|---|---|
| 前端（现在这份） | **可行，已可演示** | 单文件、无依赖、内存态，`node --check` 通过；桌面/窄屏两套布局都有断点 |
| 前端（转小程序） | **不能平移，需重写 UI** | 1120px 侧栏、`<dialog>`、`URL.createObjectURL`、`backdrop-filter` 在小程序里都没有或不等价。它只能当**信息架构与交互参考** |
| 后端最小闭环 | **可行，2–3 天量级** | 6 张表 + 4 个接口 + 幂等键。不需要 OCR、不需要跨企业排行 |
| 早起判定 | **可行且必须服务端** | 服务端权威时间 + 半开区间 + 可注入时钟；4 个边界（05:30:59 / 05:31:00 / 05:31:59 / 05:32:00）可单测 |
| 晨跑 OCR | **有条件** | 需要对象存储、内容审核、识别供应商；先用 mock adapter（带 `isMock:true` 标志）不阻塞主线 |
| 阅读时长 | **有条件，且容易被刷** | 纯客户端计时不可信。要么服务端心跳累计，要么明确"时长仅供参考、不计分" |
| 拜访 | **可行但不可验证** | 自主申报，无客户确认无定位。技术上没问题，**公平性上有问题** |
| 小组/企业排行 | **可行** | 单指标、单范围、单周期，先做这一种 |
| 省级/全国排行 | **高风险** | 需要行政区划数据 + 企业授权 + 跨企业展示字段规则；公平性无解（人少的省天然吃亏） |
| 多企业隔离 | **可行但必须一开始就做** | `enterprise_id` 从第一天进表；事后补隔离要改全部查询，代价高一个量级 |

## 4. 潜在问题

### A. 产品规则（最致命，且不是技术能解决的）

| # | 问题 | 后果 | 依据 |
|---|---|---|---|
| A1 | **"综合行动"分怎么算，完全没定义** | 四个项目量纲不同（次 / 公里 / 分钟 / 次），直接相加无意义。一旦上线，第一名是谁取决于随便定的权重 | 前端排行有"综合行动"页签，文档 §2 写"对象、得分、周期…未定" |
| A2 | **早起 59 秒窗口在产品上过窄** | 网络抖动、闹钟误差、手慢，都会产生"我明明 5:31 点的"投诉。技术上 59 秒能实现，产品上是设计缺陷 | 文档 §2「每日05:31:00—05:31:59整分钟」 |
| A3 | **拜访无法验证，却要和早起/晨跑同榜** | 一个点一下就完成的项目，和需要上传图片的项目同权重，员工会觉得不公 | §2「点一下记录，不要求拜访详情」 |
| A4 | **跨省/全国排行在 B2B 场景几乎不可行** | 企业不会同意把员工名单和出勤数据跨企业公开；即使同意，人少的省永远排后面 | §2「需要小组内、较大范围、省级、全国等范围」 |
| A5 | **内容供给是空的** | 主线是"课程关联"，但课程材料、章节、指定阅读内容都由"课程方提供"，目前一份都没有 | 前端多处写"内容待课程方提供" |
| A6 | **产品滑向考勤工具** | 5:31 打卡 + 拜访上报 + 后台统计表，员工视角这是监控不是成长。接受度决定留存 | 我的判断，非文档结论 |

### B. 技术

| # | 问题 | 后果 |
|---|---|---|
| B1 | 判定基准未定：服务端**接收时刻**还是用户**点击时刻** | 定错就等于把作弊入口留在客户端。建议接收时刻，但 UI 要有"提交中" |
| B2 | 阅读时长无心跳设计 | 前端计时改个变量就能刷满 |
| B3 | 图片重复/伪造无规则 | 同一张截图天天用也算完成 |
| B4 | `count()/4` 硬编码四项任务 | 文档说"企业自行选择打卡项目"，一旦可配置，这里立刻错 |
| B5 | 排行切换范围用同一组固定数据 | 演示可以，但评审时容易被误读成"已经能算了"（前端已有 note 提醒，合格） |
| B6 | 无持久化 | 刷新即空。演示时容易被当成"坏了" |

## 5. 优化建议（按优先级，可执行）

### P0 — 动代码之前必须做的三件

1. **写 `docs/ACTION-METRICS.md`（行动口径表）**。四个项目各一行，列：判定方式 / 有效条件 / 单位 / 单日上限 / 重复提交规则 / 异常处理 / 是否计入总分 / 是否可人工修正。
   没有这张表，后端写出来的每个判断都是猜的。这张表比任何原型都重要。
2. **更新 `DECISIONS.md`**：把 DEC-01 改成"已确认：面向其他企业员工，多企业预留"；新增 DEC-13（综合分是否存在）、DEC-14（跨企业可见范围）、DEC-15（早起判定基准）、DEC-16（阅读时长是否计分）；旧的 DEC-03 标注"新榜口径见 ACTION-METRICS"。
3. **给 TASKS 分批**：旧徒步功能统一标 `延期`（不是"阻塞"），新方向新建 T-6xx 段。否则你看任务清单会以为还有 34 件事卡着。

### P1 — 第一个可运行闭环（不依赖 A1–A4 的决策）

按文档 §4 的顺序，但砍到最小：

```
身份(测试) → 企业归属 → 课程/任务 → 团队创建/加入 → 提交一条行动记录 → 查询 → CSV 导出
```

- 6 张表：`enterprises` / `users` / `courses` / `tasks` / `teams` / `team_members` / `action_records`（含 `idempotency_key` 唯一索引）
- 4 个接口：今日任务、提交行动、我的记录、加入团队
- 早起判定做成**纯函数** `isEarlyWindow(serverTime)`，单独单测 4 个边界。这样即使规则改了，只改一个函数
- OCR / 阅读心跳 / 排行计算 **先不做**，接口留位

### P2 — 前端

- 这份 `action-preview` **冻结为设计参照**，修 C1–C3 三个小问题即可，不再加功能
- 真正要做的是**列一份小程序 UI 差异清单**：侧栏 → 底栏、`dialog` → 自定义弹层、`objectURL` → `wx.chooseMedia`、1120px 网格 → 单列 375px。这份清单决定"照着做"还是"重画"
- 加 `localStorage` 只为演示连续性，不解决任何真实问题

### P3 — 产品侧建议（我的意见，你可以否）

1. **早起窗口改成"当分钟提交即算"**（05:31:00–05:31:59 保留作为宣传口径，服务端给 10–30 秒接收容差并**在页面写明**）。59 秒不写容差，投诉量会压垮你。如果坚持 59 秒，至少要在 UI 上显示"服务器时间"而非本地时间。
2. **综合分先不要有**。第一版只做单项目榜（早起次数 / 晨跑公里 / 阅读分钟），各自独立排名。等有真实数据了再谈权重——否则权重就是拍脑袋。
3. **排行先只做「小组内 + 本周 + 单项目」**。省/全国留接口不做，避免 A4 的合规问题。
4. **拜访单独成表，不参与排行**，或权重极低。理由是它不可验证，混进榜会污染其他三项的可信度。

## 8. 本轮验证与未验证

**验证过**

| 检查 | 方法 | 结果 |
|---|---|---|
| 前端 JS 语法 | `node --check` | 通过（22,259 字符） |
| 响应式断点 | 读 CSS | `.bottom{display:none}`，≤700px 才显示底栏；1120px 网格在 ≤700px 转 block |

| 文档一致性 | 比对 README / WORKBUDDY / DEVLOG 0004 | 三处均指向新方向，旧原型标为历史 |

**未验证（不要当成通过）**

- 没有在浏览器里实际点过这 5 个页面，没有截图，没有量横向溢出。320/390 的结论是**它自己测的**，我没有复现。
- 没有 OCR、没有后端、没有数据库、没有真机、没有微信开发者工具。
- 排行"综合行动"的 19/17/16 等数值来源不明，验证不了，也不需要验证（它是布局示意）。
- 没有做可访问性的实际键盘走查，只确认样式里有焦点环。

## 9. 一句提醒

文档最后写"不反复停在泛化的'需求未定'"——这条我接受，也会照做：**不依赖未定规则的部分我立刻能开工**（表结构、幂等、窗口函数、CSV、我的记录）。
但 A1（综合分）、A4（跨企业）、B1（判定基准）这三条不能"先做着看"，因为它们决定表结构和权限模型，改起来是重写不是调整。

这三条给我结论，我当天就能出可跑的骨架。不给，我只能先把它们做成"未启用能力"——那样第一版就没有排行，只有记录。
